## Correction: the answer does not ride PCck7e

On 2026-09-25 the only thing watched was `batchexecute`, and `PCck7e` was taken for the turn. It is
not: on 2026-09-27 (`settle`, one turn, thread 659ed82f) every POST response was read whole and
searched for the token the prompt asked for.

| Response | At | Bytes | Carries the answer |
|---|---|---|---|
| `batchexecute?rpcids=PCck7e` | 2.3s | 144 | no |
| `batchexecute?rpcids=VxUbXb`, `aPya6c`, `MaZiqc` | 0.2 to 5.3s | 150 to 376 | no |
| **`POST /_/BardChatUi/data/assistant.lamda.BardFrontendService/StreamGenerate`** | **4.7s** | **10242** | **yes** |

The page held still at 4.0s (sampled once a second), the StreamGenerate body was complete at 4.7s.
So the server's own word on a finished turn is **the StreamGenerate response finishing**, and its
body carries the reply; the page is only a fallback. How to parse that body is T3's to measure.

With a picture prompt (`settle-picture`, one turn, thread in the owner's list) the picture came from
`lh3.googleusercontent.com/rd-gg-dl/` at **13.1s** and StreamGenerate finished at **15.0s** (18184
bytes, naming googleusercontent). The picture is in hand before the stream ends, so settling on
the stream and keeping the pictures seen during the turn needs no branch on the kind of job.

## Where pictures come from

`pictures` (two turns) and `peek` (no turn), host and first path segment only:

| Situation | Source |
|---|---|
| a generated picture, during its turn | `lh3.googleusercontent.com/rd-gg-dl/`, image/jpeg 12623 bytes, plus repeat fetches with no body |
| a user's upload, during the turn | a `blob:` url only (89 bytes, the 8x8 probe picture); nothing from lh3 |
| either, when the thread is reopened | `lh3.googleusercontent.com/rd-gg/` |
| the account's avatar and badge | `lh3.googleusercontent.com/a/` and `/ogw/` |

So only `/rd-gg-dl/` exactly, with a body, during the turn, is a generated picture; a loose match on
`/rd-gg` would take a reopened upload. Pinned in `tests/fixtures/gemini_image_responses.json`.

Measured through the driver on 2026-09-27 (diagnostics kept in `last_pictures`): a picture turn
brings about ten lh3 responses; of the five or so under `/rd-gg-dl/` exactly one carries the bytes
and the rest are empty repeats, alongside `/gg-dl/` text bodies of 454 bytes. One driver run that
read the bodies after the turn got no picture at all, while every run that read them the moment
they arrived did (three of three: 11806, 13909, 14165 bytes). The driver reads them at arrival; if a
turn still keeps none it fetches the `/rd-gg-dl/` urls again inside the session, a path proven on
the fake page only, never needed on the real site so far.

## Which answer is this turn's

`turn-order` (no turn) on a two-turn thread and a picture thread: each turn is a `user-query`
(the user's words, shown as "Bạn đã nói ..."), then a `model-response` holding a `message-content`
(the answer; empty for a picture-only reply), in document order. That is also why the page counts
two "bubbles" per turn. Counting bubbles cannot tell old from new when earlier turns paint late or
in steps (the tier 1 re-review reproduced an earlier answer passing for this turn's), so the driver
reads the `message-content` of the model-response after the NEWEST `user-query`, and only when that
query holds this turn's own words. `tests/fixtures/gemini_thread.html` is a captured two-turn thread
(scripts and urls stripped, no personal data) that the driver's own script runs against in
`tests/test_gemini_driver.py`. A real run afterwards: chat, same thread, a replayed multi-line
history (the anchor matched the long query as the page shows it), a picture, a video script.

Words alone cannot prove ownership: every video script job opens with the same words, and the
re-review returned an older turn's answer when this turn's question was made not to paint. So the
driver marks every `user-query` already on the page before it sends, and this turn's question is
the newest one that is NOT marked; its words are then a check, compared as a few letter words in
NFC and lower case, because a list is shown without its numbers (an `<ol>` in the real browser)
and a decomposed Vietnamese prompt is shown composed. A real run with a numbered Vietnamese list
("1. Tên: An / 2. Tuổi: 30 / Tóm tắt ...") answered "An 30 tuổi.".

The marks live on the page's own elements, so a page that rebuilt its question elements during the
turn would lose them. The questions are therefore also counted when they are marked, and this
turn's question only counts if the page then holds MORE questions than were counted: at least one
more, not exactly one, because an earlier turn that paints late adds one too. Whether Gemini ever
rebuilds or drops those elements was not measured; the count closes the case where it would. If it
ever dropped earlier turns from a long thread, such a turn would fail closed and visibly, never
return an older answer.

## Ending the wait on the stream

`Response.finished()` never returns for a stream that breaks after its 200 headers (Playwright only
resolves it on requestfinished; shown by the tier 1 review against localhost), so the driver waits
for the request's own `requestfinished` or `requestfailed` event against a deadline instead. On the
real site `requestfinished` fired for StreamGenerate in every turn of the 2026-09-27 driver runs
(chat, the same thread reopened, a replayed multi-line history, pictures, a video script).

## A failed turn

With StreamGenerate answered 500 from inside the page (`banner`, no turn reaches the server), the
page painted no `role=alert`, no snack bar and no element with an error class that the probe could
find; the reply bubble stayed empty and the address stayed `/app`. Gemini's failure is therefore
read from the StreamGenerate response itself (its status), not guessed from the page.

## Proof of sign-in

Every path answers 200 to an anonymous session too (`/app`, `/usage`, `/personalization-settings`,
fetched with `redirect: manual`), so no status proves a login. What differs is where the settings
page lands: an account stays on `/personalization-settings`, an anonymous session is sent to
`/saved-info`, which also shows role=switch buttons (two of them). `scripts/login_provider.py` now
opens that page in a tab of its own and saves only when it stays put: checked on the saved session
(True) and on an anonymous context (False).

## Personal context, the leak switch

Reading it from the settings page took **2.3s** to the switch (`aria-checked="false"` today).
The page asked the server for eight rpcids while loading (GPRiHf, sJBwce, otAQ7b, Te6DCf, maGuAc,
ESY5D, whPPme, VxUbXb); telling which one carries the switch would take flipping it, which is an
account setting and was not done. So the guard reads the settings page, and must first check that
it landed on `/personalization-settings`: signed out, the redirect to `/saved-info` also shows
switches, which are not this one.
