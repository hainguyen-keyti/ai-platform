## Findings

**F1. Should fix. Grok follow-up returns the earlier turn's answer when the read before the send fails** (`worker/src/providers/grok.py:361-371`, used at `:441`). `_baseline_ids` answers an empty set on any non-200 or non-JSON body, and `_run` sends anyway. Every earlier assistant response then counts as "new", and the first poll after START_FLOOR (`:33`, 4s) that finds `inflightResponses == []` and no new row settles on the previous answer. This is the exact class fixed for ChatGPT on 2026-10-07 (DECISIONS 2026-10-07, `chatgpt.py:540-564`), unfixed here. Scenario: a throttled free tier answers 429 to `/responses` right before a follow-up; the turn's POST is refused or slow; the person gets last turn's answer, charged. Repro `/tmp/rv_worker/grok_baseline_trap.py` (stub page, `_open`/`_send` stubbed): baseline read 200 → control runs to the 300s ceiling as `provider_timeout`; baseline read 429 or 500 → `success=True text='The capital of France is Paris.'` after 4s, sent 1. Fix: make `_baseline_ids` retry and then raise `ProviderError` with nothing sent, as `chatgpt.py:549-564` does; pin it in `test_grok_settle.py` (red first with a 429 baseline).

**F2. Should fix. A dead browser turns the runner into a fast-fail loop, not just "no recovery"** (`chatgpt.py:301-306`, `grok.py:132-137`, `gemini.py:194-199`, `pool.py:184-186`, `pool.py:48-55`). `_ensure_page` hands back the same closed page forever (known point 3 of the session plan). What that plan did not say: `TargetClosedError` is a plain `playwright Error(Exception)` (`playwright/_impl/_errors.py:26,52`), so `pool.execute` maps it to `worker_error`, which `ProviderHealth.note` neither cools down nor counts. With `min_gap` 0 (ChatGPT's default) the runner claims the next job one second later and fails it the same way: the whole queue burns at about one job per second, every one refunded with "TargetClosedError" as the person's error, health still `ready: true`, until someone restarts the Terminal tab by hand (DECISIONS 2026-10-06). Triggers: a Chromium crash, cloakbrowser's self-updated binary (known point 6), the profile lock lost. Fix: in each driver, when a Playwright call raises an `Error` whose text says the target or browser is closed, run `stop()` (drop `_context`/`_page`) and re-raise as `ProviderError` so the next job reopens the profile under a cooldown; one fake-page check per driver (a page whose `goto` raises `TargetClosedError` once, the next `_run` opens anew).

## Lifecycle and threading: what the code says (section 1, confirmed)

- Claim, lease, heartbeat and 409 match the api: heartbeat every `min(lease/3, 5)` = 5s (`runner.py:142`), renews the lease and notes the worker (`jobs.py:370-379`); `alive: false` sets `lost`, the driver checks it every 1s (`chatgpt.py:590,727`, `gemini.py:472`) or 2s (`grok.py:451`, `gemini.py:598`), so a stop acts within about 6-7s; "learns within 5s" holds. ChatGPT presses the site's stop and records it (`:886-900`).
- A refused result (409) removes that attempt's files (`runner.py:219-223`); the api tombstones or adopts the thread of a cancelled job first (`jobs.py:401-421`). Measured in mock only (known).
- Tombstones run during pacing gaps and image-budget waits, never during an error cooldown (`runner.py:76-79`, `pool.py:130-133`), one per 10s per provider, kept alive by a pinger (`:124-132`).
- Liveness: pings every 5s or less in a hold (`runner.py:72-80`), via the heartbeat in a job, via `_keep_alive` after a lost job and during a deletion, via the claim when idle; the api's window is 310s (`api/src/config.py:38-39`). The only gap is the known one: a heartbeat answered non-200 neither pings nor sets lost.
- Cooldown math: 30s × 2^(n-1), capped at 900s, counted only for `provider_error`/`provider_timeout`, reset only on success; `provider_misconfigured`, `cancelled` and `worker_error` neither count nor reset (`pool.py:48-60`), which is what makes F2 a loop. The api's 600s hold refuses new turns and fails the waiting ones (`jobs.py:116-126,220-240`).
- Browser dead at start: `open_session` raises `ProviderError` (`session.py:71-77`) → cooldown; fine. Mid-job: F2. Restart mid-job: the lease expires, attempt 2 re-sends (`jobs.py:176-201`).
- `run-worker.sh` binds 127.0.0.1 (`:40`), sources `.env` as shell (`:20-22`, the api's secrets enter the worker's environment; nothing prints them), installs pinned requirements each start (`:28`; no network needed when satisfied). No logging module in the worker at all; every error string I traced carries a thread id, a status or the page's last 120 characters (`grok.py:422-430`), never a token or cookie; the Google block url is stripped (`gemini.py:151-157`). `login_provider.py` prints cookie names only (`:214-220`). `.gitignore` covers `storage/`.
